# Decision: 快捷安排与详情草稿的写入边界

Status: implemented

源码、构建及本地试装包验证见 [验证记录](../../EVIDENCE-task-arrangement.md)，不代表安装升级已经验收。

## Problem

任务行、周卡片和周拖放都需要直接修改执行计划。通用任务更新会清空提醒已通知标记；只在当前窗口检查草稿无法保护其他窗口尚未落盘的输入。详情还持有独立缓存，计划更新后不能把旧计划带入下一次正式保存。

## Decision

- `TaskCommands.arrange` 是快捷安排唯一写入者，输入任务编号、所见修改时间、数据代际和动作。相对日历目标由主进程提交时解析；自定义日、周、月目标规范化后保存。
- IPC 使用现有 `WindowBarrier`：准备 → 所有窗口暂停编辑并保留草稿 → 确认完成后锁定写入 → 同步结果 → 恢复交互。仍采用现有十秒确认期限；超时、保存中或落盘失败均不执行安排，恢复所有窗口。
- SQLite 事务检查代际、任务版本、未完成顶层状态及目标任务草稿。存在未正式提交草稿时拒绝，不合并、不丢弃、不自动提交。此限制不加到正式详情提交上。
- 只写 `plan_json`、`focus_date`、单调递增的 `updated_at`；截止、提醒、已通知标记、重复规则、排序等均不变。同目标不写入、不广播业务变更。
- 成功恢复消息携带任务和干净草稿快照。协调器先同步无未保存修改的目标缓存，再恢复编辑；在途编辑器读取不得重新插入旧内容。恢复备份会作废已打开的安排窗口及迟到请求。
- 今日重点与普通置顶分离。重点安排到今天，取消仅清除重点；改变日或精度清除原重点。周拖放与任务行共用安排控制器和主进程命令，正式详情仍显式保存。
- 本次内部 IPC 契约与 preload、renderer 同版本交付；无兼容层、数据库迁移或备份版本变动。延续 [独立草稿决策](2026-09-07-editor-drafts.md)，不改批量任务命令的行为。

## Alternatives considered

- 调用通用 `updateTask`：会清空提醒标记，且没有快捷操作所需的版本与草稿校验。
- 只读取当前窗口草稿：不能覆盖其他窗口尚未提交的输入，也不能消除检查与写入之间的竞争。
- 自动提交或合并草稿：改变明确的手动保存语义，可能让用户不想保存的其他字段生效。
- 新增表、全局状态框架或独立写入服务：现有草稿、事务和窗口屏障足以承担该职责。

## Consequences

普通行、提醒、周卡片和拖放共享安排规则；代价是快捷安排需要等待窗口确认，目标存在草稿时必须先到详情处理。失败保留安排面板和错误，不以短暂提示替代处理入口。快速捕获新增关闭按钮，但保留草稿与正式保存仍是两种动作。

## Verification

验证覆盖窄字段不变性、无操作写入、午夜及跨年、规范化、版本/代际/状态拒绝、窗口超时与失败恢复、干净缓存及在途读取同步、搜索与标签筛选、键盘和周拖放。真实 Electron 使用临时 SQLite 与双窗口验证；localhost 浏览器模拟接口只证明界面，不证明真实持久化。详见独立验证记录。

## Rollback

正常退出后整体回退主进程、preload 与 renderer，不单独替换 IPC 任一端。本次没有新表或备份版本，已安排任务仍使用原计划字段；回退应用不会自动撤销已保存的执行计划。未执行打包、安装、发布或个人数据库操作。
